## 要望①: 1/8 細分メッシュ（125m・11桁）対応

### 1. 背景・ユースケース

親プロジェクトでは、国土交通省「国土数値情報」の公開ハザードデータ（洪水浸水想定 A31a/A31b、土砂災害警戒区域 A33、内水浸水 A51、多段階浸水想定 A53）を災害移動制約エリアとして取り込む機能を計画している。

- 取り込んだポリゴンは**125m メッシュ（JIS X 0410 1/8 細分・11桁）にラスタライズ**し、既存の `RestrictedAreaService.AddBlockArea / AddDifficultyArea(IEnumerable<MeshCode>)` で登録する方針（ユーザー合意済み）
- 親側のエージェント・廃棄物管理メッシュは従来通り最大 250m（10桁）のまま。**125m は移動制約エリア専用**
- 250m では土砂災害警戒区域（幅数十mの小区域多数）や浸水縁の形状が粗くなりすぎるため、1階層下が必要
- 親側の活動効果判定・描画は `MeshCode.ToBounds()` 委譲で実装済みのため、**ライブラリが11桁対応すれば親側ロジックは自動追従**する

`MeshCode.cs` の remarks に「11 桁（1/10 細分 = 100m）は仕様未確定のため Phase 2 以降で対応予定（REQ-RST-016 参照）」とあり、本要望はこの**仕様確定の提案＋実装依頼**にあたる。

### 2. 仕様提案: 「1/8 細分（象限方式）」の採用

JIS X 0410 には 3次メッシュ（8桁）より細かい区画として2系統があり、桁数に曖昧性がある:

| 方式 | 桁構成 | 一辺 | 備考 |
|------|--------|------|------|
| 分割地域メッシュ（象限方式） | 9桁=1/2（500m）、10桁=1/4（250m）、**11桁=1/8（125m）** | 各桁 1〜4 | 既存 9・10桁実装の自然な延長 |
| 10分の1細分区画 | 8桁＋2桁（00〜99）=10桁（100m） | 100m | **既存の 1/4 細分（10桁）と桁数衝突** |

**提案: 11桁目=象限1〜4 の「1/8 細分（125m）」を正式仕様として採用**する。

- 理由1: 既存の `MeshLevel.HalfMesh`（9桁）/ `QuarterMesh`（10桁）と同じ象限再帰なので、`MeshCodeConverter` の分割ロジックをそのまま1段深くするだけで済む
- 理由2: 桁数→階層の一意判定（`MeshCode.Level` の switch）が維持される。10分の1細分区画（10桁・00〜99）を採用すると既存 1/4 細分と判別不能になる
- 理由3: 親ユースケース（ハザード形状の保持）には 125m で十分（さらに細かい階層は当面不要、とユーザー確定済み）
- remarks の「1/10 細分 = 100m」記載は上記の桁数衝突があるため、1/8 象限方式への読み替えを提案する

### 3. 要望内容（API 契約）

既存 API のシグネチャ変更なし。11桁の `MeshCode` 値が全 API で 8〜10桁と同等に扱えること。

1. **`MeshCode.Level`**: 11桁（`10_000_000_000 〜 99_999_999_999`）で新階層（例: `MeshLevel.EighthMesh`）を返す。範囲外例外の上限を11桁超に更新
2. **`MeshCodeConverter.ToBoundingBox`**: 11桁目（1〜4）の象限で 1/4 メッシュをさらに4分割した矩形を返す（緯度 3.75秒 ≒ 115.7m、経度 5.625秒）。桁値 0/5〜9 は既存細分桁と同様に `ArgumentException`
3. **`MeshCode.EnumerateInBounds(bounds, level)`**: 新階層を指定可能に（南西→北東走査の既存契約を維持）
4. **`RestrictedAreaService.AddBlockArea / AddDifficultyArea(IEnumerable<MeshCode>)`**: 変更不要のはず（`Shape.FromMesh` → `ToBoundingBox` 経由のため 2. の対応で自動）。11桁混在の動作確認のみ希望

### 4. 受け入れ基準（提案）

1. `new MeshCode(52366610_1_11桁).ToBounds()` が親メッシュ（10桁）の対応象限の南西/北東と厳密一致（境界共有）
2. 同一 3次メッシュ内の 64 個の 1/8 メッシュが隙間・重複なくタイリングする
3. `EnumerateInBounds` が 8〜11桁の各階層で同一 bounds に対し整合した個数を返す（1/8 は 1/4 の縦横2倍）
4. 11桁メッシュを `AddBlockArea(meshCodes)` で登録した経路計算で、当該 125m 矩形と交差するエッジのみが遮断される（既存 AABB 交差セマンティクス＝REQ-RST-015 の踏襲）
5. 既存 8〜10桁の全テストが無変更でパスする

### 5. 性能に関する所見（参考）

親側では市町村規模マップ（例: 12km×10km）で**最大数千〜数万件の 11桁メッシュを単一 `AddBlockArea/AddDifficultyArea` 呼び出しで一括登録**する想定。`Register` → shape ごとの `SpatialIndex.Add` + `BakeIntoCache`（AABB クエリ）の既存構造で問題ない認識だが、万一階層追加で性能上の留意点があれば教えてほしい。

## 要望②: GmlParser のフィーチャ属性公開

### 1. 背景・ユースケース

国土数値情報のうち **A51（雨水出水・内水浸水想定区域）のみ GeoJSON が提供されておらず GML のみ**（2025年度版で実確認。`A51-25_{都道府県}_GML.zip` のみ存在し `_GEOJSON.zip` は404）。

親側は GML から**フィーチャごとの属性**（浸水深ランク等）を読み、「ランク2=移動困難（冠水）/ ランク3以上=移動不能」のように制約レベルへ振り分けてから、125m メッシュへラスタライズして登録する。つまり**形状と属性のペア**が必要。

OsmDotRoute には KSJ アプリケーションスキーマ準拠の `GmlParser`（REQ-RST-020〜028）が実装済みだが、`ParseString / ParseStream` は `IReadOnlyList<GeoPolygon>`（形状のみ）を返し、属性が取得できない。`AddBlockAreaFromGml` 系も同様に形状のみの一括登録となる。

### 利用側で再実装しない理由
- KSJ GML（JPGIS）の `gml:Polygon` / 内環 / xlink 参照解決は GmlParser が既に正しく処理している。親側で属性のためだけに GML 形状パーサを二重実装するのは無駄が大きい
- 属性はフィーチャ要素直下の単純な子要素（例: `<ksj:A51_001>…</ksj:A51_001>` 相当）であり、形状走査と同じパスで取得できる見込み

### 2. 要望内容（API 契約案）

フィーチャ単位で「形状＋属性」を返す公開 API の追加。シグネチャは裁量に委ねるが、例として:

```csharp
/// <summary>KSJ GML のフィーチャ（形状＋属性）。</summary>
public sealed record GmlFeature(
    GeoPolygon Polygon,
    IReadOnlyDictionary<string, string> Attributes);  // key=要素ローカル名（例 "A51_001"）、value=テキスト内容

public static class GmlParser
{
    // 既存 ParseString/ParseStream はそのまま維持
    public static IReadOnlyList<GmlFeature> ParseFeaturesStream(Stream stream);
    public static IReadOnlyList<GmlFeature> ParseFeaturesString(string gml);
}
```

- 属性値は**文字列のまま**で良い（型解釈・コードリスト解決は利用側責務）
- 名前空間 prefix は剥がしてローカル名キーで良い（KSJ の属性名 `A51_001` 等が一意のため）
- ジオメトリを持たないフィーチャ・対応外ジオメトリのスキップ方針は既存パーサの挙動踏襲で可
- 大容量対応: A51 は小さい（愛知県 0.6MB）ため、ストリーミング yield でなくリスト返却で十分

### 3. 受け入れ基準（提案）

1. KSJ A51 の GML 実ファイルで、フィーチャ数・各フィーチャの `A51_*` 属性・外周/内環座標が取得できる
2. 既存 `ParseString / ParseStream` / `AddBlockAreaFromGml` 系の挙動・テストが無変更でパスする
3. 属性が1つも無いフィーチャでも空 Dictionary で返る（例外にしない）

### 4. 補足

- 親側の取り込み対象は市町村規模であり、A51 実データに `gml:MultiSurface` が含まれる場合（現状 REQ-RST-023 で `NotSupportedException`）の扱いは、まず親側で対象自治体の実データを確認してから必要なら別途相談する（本要望のスコープ外）

## 親プロジェクト側の利用計画（参考・本要望のスコープ外）

1. KSJ ZIP をツール内自動ダウンロード（直接URL方式・実証済み）→ GeoJSON（A31a/A31b/A33/A53）は親側 `System.Text.Json` でパース、A51 のみ本要望②の API でパース
2. フィーチャ属性→制約レベル振り分け → **125m メッシュへラスタライズ**（微小セルは AABB 交差、大ポリゴンは中心点 in ポリゴン）
3. 既存 `DisasterArea.MeshCodes`（文字列リスト）に格納 → `ApplyPhaseConstraints` から `AddBlockArea/AddDifficultyArea(meshCodes)` で登録（親側モデル・セーブ形式は無変更）
